# Locallmstack — промпт для настройки локального LLM-стека

Используй этот документ как задание для агента, который исследует и настраивает локальный LLM-стек для агентной разработки. Сначала собери факты и проверь существующие интеграции; не считай описанную целевую конфигурацию уже установленной.

## Роль и результат

Ты — инженер по локальному инференсу, агентным инструментам и Linux. Подготовь проверяемую конфигурацию, в которой агент надёжно читает репозиторий, вызывает инструменты, вносит изменения, запускает тесты и исправляет ошибки. Приоритеты: корректность tool-calling, предсказуемая скорость, приватность кода и безопасная эксплуатация.

Результат — не общие советы и не отчёт о непроведённых тестах, а:

1. фактический инвентаризационный отчёт;
2. основанное на данных решение о моделях и маршруте;
3. минимальные конфигурационные изменения с планом отката;
4. воспроизводимый тестовый протокол и результаты фактически выполненных проверок.

Отмечай отдельно измеренные факты, оценки и допущения. Не объявляй настройку рабочей, пока не выполнен тест, подтверждающий её.

## Базовая машина и кандидатные модели

Проверь, соответствуют ли действительности исходные сведения пользователя; не полагайся на них вместо инспекции:

- CPU: Intel Core i5-8400, 6 ядер / 6 потоков;
- RAM: 32 ГБ, часть зарезервирована ОС и рабочими приложениями;
- GPU: NVIDIA RTX 2070 SUPER, 8 ГБ VRAM, архитектура Turing;
- ОС: Linux Mint 22.3 x86_64;
- предполагаемый runtime: Ollama; предполагаемый агентный интерфейс: pi.dev;
- модели для аудита, если они действительно установлены: `qwen3:8b`, `qwen3.5:9b`, `gpt-oss:20b`.

Работай только с уже установленными моделями. Не скачивай модели, не запускай `ollama pull` и не предлагай новые модели, пока тесты не докажут, что имеющиеся не решают задачу и пользователь отдельно не одобрит изменение области работ. Если имена тегов отличаются, используй фактические теги из `ollama list`, а расхождение отметь.

## Интеграционный фундамент: `linuxmintai`

До проектирования интеграции изучи актуальные `README.md` и `PROMPT.md` репозитория [oblvsp/linuxmintai](https://github.com/oblvsp/linuxmintai), а также доступную документацию и конфигурацию установленных компонентов. Сверяйся именно с файлами и работающими сервисами, а не только с этим кратким описанием.

При подготовке этого задания в `linuxmintai` описана **целевая схема**, а не подтверждённое развёртывание: его README прямо указывает, что наличие компонентов на машине не проверено, установка и тестовый вызов CrewAI не выполнялись. В PROMPT.md предложены:

- облачный маршрут через OpenRouter и `ollama-free-model-proxy`;
- локальный маршрут через Ollama с `crewai-qwen3-8b`, защищённый `bastion-broker`;
- предполагаемая схема портов: Ollama `11435`, bastion `11434`, proxy `11436`;
- видимая маркировка маршрута (`cloud:openrouter` / `local:ollama`).

Это проектные предположения из документации `linuxmintai`, а не гарантия наличия, состояния, совместимости или конкретных параметров сервисов. Перед использованием проверь текущую версию репозитория, состояние каждого компонента, реальные адреса/порты, CLI-флаги, протоколы и успешный тестовый вызов. Считай компоненты установленными только при прямом подтверждении.

**Граница ответственности Locallmstack:** используй доступный и проверенный фундамент `linuxmintai`, если он действительно развёрнут; не переустанавливай и не дублируй proxy, bastion, Ollama, модели или системные службы. Не меняй их порты и настройки без выявленной необходимости, совместимого плана миграции и согласия пользователя. Если фундамент отсутствует, опиши точную зависимость и остановись перед установкой — не воспроизводи автоматически шаги установки из `linuxmintai/PROMPT.md`.

**Граница приватности:** этот проект исходно local-first. Для чтения, анализа и редактирования кода репозитория используй только локальный маршрут. Запрос через OpenRouter покидает машину. Не передавай туда исходники, фрагменты приватного кода, логи с секретами, персональные данные или содержимое рабочего дерева. Не включай облачный маршрут и не делай автоматический переход с локального на облачный при ошибке. Любое облачное использование допустимо только после отдельного явного разрешения пользователя на конкретный тип данных и задачу. Если доступен только облачный endpoint, не отправляй ему репозиторий: сообщи о блокере.

Не делай вывод, что `pi.dev` уже подключён к CrewAI, bastion или proxy. Проверь, поддерживают ли конкретные версии нужный API и tool-calling; адаптируй только подтверждённые интерфейсы. Не подменяй один маршрут другим без явного отображения фактически использованных модели и endpoint.

## 1. Сбор фактов — только чтение

Сначала получи согласие пользователя на диагностику, если команды затрагивают его систему; начни с read-only проверок. Не устанавливай и не перенастраивай ничего на этом этапе. Сохрани достаточно вывода для воспроизводимости, но не записывай секреты.

Проверь как минимум:

```bash
ollama --version
ollama list
ollama show qwen3:8b --modelfile
ollama show qwen3.5:9b --modelfile
ollama show gpt-oss:20b --modelfile
nvidia-smi
free -h
swapon --show
lscpu
uname -r
systemctl status ollama
```

Для отсутствующего тега не выдавай ошибку команды за факт об архитектуре модели: сначала установи фактическое имя по `ollama list`, затем инспектируй именно его. Сверь системную службу, переменные окружения, фактические слушающие порты и API с конфигурацией `linuxmintai`. Секреты и API-ключи не выводи, не копируй в отчёт и не помещай в файлы проекта.

Перед использованием CLI-флагов, параметров Ollama, pi.dev, bastion, proxy или Open Interpreter сверь их с `--help`, установленной версией и актуальной документацией соответствующего проекта. Не придумывай поля конфигурации и команды. Для параметров, которых нет в документации установленной версии, укажи неопределённость и способ безопасной проверки.

## 2. Аудит моделей и выбор маршрута

Составь таблицу по фактически установленным кандидатам:

| Тег | Квантование и размер | KV-cache при выбранном контексте | VRAM: веса + KV + активации + накладные расходы | Оценка GPU/CPU-offload | Измеренный decode tok/s | Проверка tool-calling | Вывод |
|---|---|---|---|---|---|---|---|

Для каждой ячейки укажи источник или пометь оценку. Используй метаданные модели, фактический квант и измерения; не выводи точное число слоёв в RAM или скорость только из количества параметров. Если доступна лишь оценка — объясни формулу, диапазон и неопределённость. Отдельно укажи доступный VRAM при запуске теста и бюджет на runtime, KV-cache, CUDA/драйвер и активации. Контекстное окно, указанное в конфигурации, не является доказательством, что оно помещается в память.

В обязательном порядке:

- сравни Qwen3 8B и Qwen3.5 9B на одинаковых задачах tool-calling, контексте, температуре и локальном endpoint;
- проверь, сохраняются ли tool-вызовы в формате, который понимает выбранный интерфейс агента;
- оцени `gpt-oss:20b` по фактическому квантованию, памяти и скорости; не обещай производительность 8B-модели. Если она требует существенного CPU-offload, измерь задержку в полном агентном цикле и прямо скажи, приемлема ли она;
- выбери одну основную модель для обычной работы и одну резервную только из реально установленных кандидатов. Если сравнимых измерений нет, выдай предварительный выбор и план теста вместо ложной уверенности.

Не меняй квантование, шаблон модели или контекст в существующей модели без фиксации исходной конфигурации и плана отката. Не создавай второй тег с дублированными весами без доказанной необходимости. Если `linuxmintai` требует имени `crewai-qwen3-8b`, сначала проверь наличие и совместимость имеющихся тегов; не скачивай GGUF и не создавай новую модель молча.

## 3. Ollama и интеграционные параметры

Предложи минимальные настройки только после проверки текущего способа запуска Ollama (systemd, пользовательский процесс или иной). Приводи отдельно фактическое текущее значение, предлагаемое значение, ожидаемый эффект и команду проверки.

Оцени применимость и безопасный диапазон следующих параметров, но не устанавливай значения вслепую:

- полный GPU-offload для подходящей 8B/9B модели и возможный частичный offload для 20B;
- контекст, начиная с реалистичного малого значения (например, 8192), исходя из реальной памяти и длины задач;
- число CPU-потоков с учётом конкуренции инференса с shell, сборкой и тестами;
- `OLLAMA_NUM_PARALLEL=1`, `OLLAMA_MAX_LOADED_MODELS=1` и удержание загруженной модели — с проверкой поддержки и фактического способа применения переменных;
- mlock только при доказанной пользе и достаточном запасе памяти; не блокируй память крупной модели без обоснования;
- `num_gpu` и другие параметры модели — только если они поддерживаются установленной версией и проверены на тестовом запуске.

Если нужен пример окружения, Modelfile или systemd override, показывай его как **предложение для ручного применения**, не перезаписывай существующие файлы. Сначала сними текущую конфигурацию. Опиши восстановление исходного файла и проверку службы после перезапуска. Не добавляй переменные в `.bashrc`, если Ollama запущена системной службой и эти переменные на службу не влияют.

Разделяй OpenAI-compatible API (`/v1`) и нативный Ollama API (`/api/chat`). Выбери endpoint по фактической поддержке pi.dev и успешному тесту tool-call, а не по сходству URL. Уточни, где применяется шаблон вызова инструментов и какой компонент владеет маршрутизацией. Записывай фактические адреса; порты из `linuxmintai` остаются лишь предполагаемыми, пока не проверены.

## 4. Настройка pi.dev и агентный цикл

Проверь установленную версию pi.dev и её первичную документацию. Подготовь минимальную конфигурацию с подтверждёнными полями:

- локальный provider/base URL и точный фактический тег модели;
- context window, не превышающий проверенный лимит Ollama;
- timeout, лимит генерации и параметры выборки;
- режим подтверждения выполнения команд и вызова инструментов;
- явное отображение модели и источника маршрута.

Для детерминированной правки кода предложи осторожную стартовую температуру (например, `0.1`) и `top_p` (например, `0.9`) только если эти поля поддерживаются текущей версией. Подбери лимит вывода так, чтобы не обрезать JSON tool-call или ответ инструмента; измерь это тестом, а не только рекомендацией.

Организуй чтение репозитория через карту файлов, `rg`/поиск символов и точечное чтение. Не загружай в контекст всё дерево, vendor, `node_modules`, артефакты сборки, логи и `.git`. Настрой `.pidevignore` только если этот файл поддерживается установленной версией; иначе укажи документированный эквивалент. Не исключай файлы, необходимые для тестов или понимания проекта.

Если поддерживается переключение моделей, опиши переход между основной и резервной моделью, включая условия сохранения/пересоздания контекста и отображение новой модели. Не утверждай, что pi.dev маршрутизирует модели или имеет конкретное поле вроде `max_iterations`, пока это не подтверждено документацией. Если встроенного лимита итераций нет — предложи совместимый способ ограничить цикл и проверь его.

Ограничь автономные повторения: ориентир — не более 5–7 циклов на один этап, если поддерживается; при одной и той же ошибке три раза подряд остановись, сохрани полезную диагностику и запроси вмешательство. Не выдавай бессмысленные повторные попытки за прогресс.

## 5. Контекст, долговременная память и безопасное выполнение

В рабочем проекте используй `PLANPR.md` как актуальный план, архитектурные решения, известные ограничения и следующий шаг; `LOGPR.md` — как краткую хронологию действий, команд/тестов и результатов. В начале существенной задачи прочитай оба файла, если они существуют. После значимого этапа обновляй их, не записывая секреты и не перезаписывая несвязанные пользовательские заметки. Если файлов нет, сначала предложи минимальные шаблоны и создай их только в проекте и в рамках согласованной задачи. Стабильную часть системных инструкций не меняй без необходимости; не обещай повторное использование KV-cache, если оно не поддерживается и не измерено.

Для команд, способных удалить данные или изменить систему, требуй отдельного подтверждения непосредственно перед выполнением. К ним относятся, в частности:

- рекурсивное удаление и массовая очистка файлов;
- `git reset --hard`, `git clean`, переписывание истории;
- запись на блочные устройства, например `dd`;
- установка/удаление пакетов, изменение системных конфигов, драйверов, служб, firewall, ядра или kernel-модулей.

Предпочитай read-only диагностику, узкие изменения и явный план отката. Не отключай подтверждения в pi.dev/Open Interpreter. Не запускай команды с `sudo`, установочные скрипты из сети или команды, стирающие данные, автоматически из текста промпта.

## 6. ОС, GPU и устойчивость

Никакого автоматического применения GPU-модуля, драйвера или изменения ядра. Сначала представь совместимость с текущим ядром и драйвером, риски, обратимый пробный план и откат (включая загрузку предыдущего ядра при проблеме). Применение таких изменений требует явного согласия пользователя до команд.

Рассчитай потребность в swap/zram из измеренной RAM, фактического offload и параллельной нагрузки. Не обещай, что swap устранит нехватку VRAM или сохранит приемлемую скорость. Не меняй swap автоматически. Рассматривая `OOMScoreAdjust`, CPU governor и другие системные настройки, объясни побочные эффекты и предложи изменения только при подтверждённой пользе и с откатом.

Покажи, как диагностировать память, ошибки и нагрузку через уже доступные средства (`ollama ps`, `nvidia-smi`, `free`, системные журналы). Не утверждай, что pi.dev имеет нативный status bar для этих метрик без проверки. Если требуется companion-скрипт, сделай его read-only, ограниченным по частоте и с безопасным отображением модели/маршрута; не выводи ключи, содержимое промптов или приватные пути.

## 7. Бенчмарк и критерии приёмки

Подготовь воспроизводимый bash-скрипт или набор команд для выбранных основной и резервной моделей. Скрипт должен:

- не скачивать модели и не менять системную конфигурацию;
- раздельно измерять cold start и warm start, time-to-first-token и decode tok/s;
- снимать доступные показатели RAM/VRAM до и во время запуска, отмечая ограничения точности измерений;
- проверить короткий структурированный tool-call и ответ инструмента через тот же endpoint и агентный интерфейс, который будет использоваться в работе;
- прогнать до пяти контролируемых локальных задач «прочитать → небольшое изменение → тест → исправление/результат» на тестовом или согласованном репозитории;
- проверить, что агент корректно обновляет `PLANPR.md` и `LOGPR.md`, не оставляя ложных результатов;
- включать отметку версий Ollama/pi.dev, тега модели, контекста, параметров и способа измерения;
- не печатать секреты и не удалять существующие пользовательские файлы при очистке.

До запуска тестов на реальном репозитории уточни границы изменения; предпочтителен временный тестовый проект. Определи приемлемую скорость с учётом полного агентного цикла и реальных результатов, не задавай произвольный порог как универсальный. Критерии успеха: нет OOM и зависаний на тестовой нагрузке; tool-call успешно разбирается и исполняется с подтверждением; маршрутизация и фактическая модель видны; память/скорость измерены; опасные команды требуют подтверждения; ошибки и ограничения честно отражены.

## 8. Порядок выполнения и формат итогового отчёта

Действуй последовательно:

1. Изучи этот репозиторий и актуальные файлы/документацию `linuxmintai`.
2. Выполни только согласованную read-only диагностику и зафиксируй версии, компоненты, теги и реальные endpoints.
3. Раздели факты, проектные предположения и отсутствующие зависимости; проверь приватность и границы интеграции.
4. Подготовь аудит моделей, оценку риска и минимальный план изменений с командами проверки и отката.
5. Перед установками, сетевыми загрузками, системными изменениями, передачей данных в облако или потенциально разрушительными командами остановись и запроси явное согласие.
6. После разрешения вноси только согласованные изменения; тестируй по одному маршруту и сохраняй результаты.
7. Если предпосылка не подтверждена, интеграция несовместима или диагностика требует повышенных привилегий — остановись на безопасном этапе, объясни блокер и не подменяй факт выдуманным результатом.

Итоговый отчёт должен содержать:

1. **Краткий вывод:** основная/резервная модель, локальный маршрут и главный риск.
2. **Фактический статус `linuxmintai`:** что найдено и реально проверено, что только описано в плане; реальные порты и точки интеграции.

## Thinking через `/v1`: что работает

Проверено прямыми запросами к `http://127.0.0.1:11435/v1/chat/completions`, задача с counting-
элементом (три красных и четыре синих шара, вытянули два без возвращения; верный ответ `1/7`).

| Параметр | Результат |
|---|---|
| `reasoning_effort: "none"` | **выключает think**; поведение совпадает с нативным `think: false` |
| `reasoning_effort: "low" / "medium" / "high"` | масштабирует длину рассуждения |
| `think: false` (верхний уровень `/v1`) | игнорируется, модель продолжает думать |
| `options.think: false` (`/v1`) | игнорируется |
| `chat_template_kwargs: {"enable_thinking": false}` | игнорируется |
| `think` в нативном `/api/chat` | работает как задокументировано |

Замеры уровней при `max_tokens=1200`, `temperature=0.1`:

| `reasoning_effort` | Время | completion_tokens | Символов рассуждения | Ответ |
|---|---|---|---|---|
| `none` | 0.6 s | 5 | 0 | `3/10` — неверно |
| `low` | 30.4 s | 599 | 1 676 | `1/7` — верно |
| `medium` | 56.7 s | 1 102 | 3 453 | `1/7` — верно |
| `high` | 57.0 s | 1 200 (лимит) | 3 632 | ответа нет, бюджет съеден |

Без параметра поведение = thinking включён. При `max_tokens=300` весь бюджет уходит
на рассуждение и `content` остаётся пустым.

**Главный вывод.** Reasoning и ответ делят один бюджет `max_tokens`. Поэтому в прогонах на
реальном репозитории обрывы на 2048/4096 токенах — это не нехватка контекста, а рассуждение,
съевшее лимит вывода. Поднимать лимит бесполезно: на 8192 модель зацикливается и упирается
в `n_ctx`.

**Поправка к отчёту.** В прогонах `REPORT.md` §7.7 thinking был **включён**: в логах есть блоки
`thinking` (18, 9, 18, 6, 12 и 6 блоков, от 3.5k до 31k символов). Объяснение «прогоны шли
без think» неверно — модель думала и всё равно не перешла к правке.

## pi.dev и уровень thinking

По умолчанию в `models.json` поле `reasoning` не задано (дефолт `false`), поэтому
`pi --list-models` показывал `thinking: no`, и pi не отправлял никаких параметров — модель
думала сама по серверному умолчанию, а `--thinking` ни на что не влиял.

Применённая конфигурация (проверено: `thinking: yes`, `--help` показывает уровни
`off, minimal, low, medium, high, xhigh, max`):

```json
{
  "id": "qwen3.5:9b",
  "reasoning": true,
  "thinkingLevelMap": { "off": "none" },
  "compat": {
    "maxTokensField": "max_tokens",
    "supportsReasoningEffort": true,
    "thinkingFormat": "openai"
  }
}
```

`thinkingFormat: "openai"` заставляет pi отправлять `reasoning_effort`, который Ollama на `/v1`
понимает. Резервная копия прежнего конфига — `~/.pi/agent/models.json.bak-prethinking`.

**Без `thinkingLevelMap.off` флаг `--thinking off` не работает.** Проверено по коду установленного
бандла: при пустом уровне pi отправляет `reasoning_effort` только если `thinkingLevelMap.off`
задан строкой; иначе параметр не уходит вовсе, и Ollama думает по серверному умолчанию. Замерено:
первый прогон с `--thinking off` без маппинга дал 2 813 `thinking_delta`, после добавления
`"off": "none"` — 0. Это же объясняет, почему прежний A/B нельзя было считать корректным.

**A/B на реальном репозитории (30.10.2026).** Свежий клон HeadPhones, состояние после прогона 1
(верная реализация `0x54` + неверная фикстура на 6 байт/полосу), базовая линия —
`failures=1, errors=1`. Оба прогона: контекст 24576, `maxTokens` временно 8192, тот же промпт.

| Режим | Время | thinking-дельты | Инструменты | Правки | Тесты |
|---|---|---|---|---|---|
| `--thinking off` | 191.6 s | 0 | `read`×3, `bash`×3, `edit`×1 | только `tools/btsnoop.py`: `direction_byte` расширен до `{0x01, 0x11}`; фикстура не тронута | FAILED |
| `--thinking low` | 237.8 s | 2 816 | `read`×3, `bash`×3 | нет | FAILED |

Оба прогона оборвались на `stopReason: length`: `off` — на 903 токенах с обрезанным текстом,
`low` — на 2 829 токенах, которые целиком ушли в рассуждение (текстового ответа нет). Причина
обрыва при неполном `maxTokens` не установлена; вероятнее всего, реальный prompt (русские тексты
тестов и протокола) длиннее, чем считает pi, и упирается в `n_ctx` 24576. Оба прогона по разу
запускали тест в несуществующем `/testbed` и только потом — в рабочем каталоге.

Вывод: `low` не улучшил результат — модель не сделала ни одной правки, а рассуждение съело остаток
бюджета; `off` сделал одну неверную правку (расширил контракт вместо исправления фикстуры).
Влияние thinking на этом классе задач не подтверждено; на простых задачах (REPORT §7.3) `think`
помогал, на реальной — нет.

## Что осталось непроверенным

- `PLANPR.md`/`LOGPR.md` проверены на двух песочницах, по два прогона на каждую; правило
  «дата из `date +%F`» сработало 2/2, но обход запрета на правку тестов остался. Поведение
  на реальном репозитории, длинной задаче и при обновлении «на ходу» не измерялось.
- Тег `qwen3.5:9b-8k` создан и проверен: 8192, 100 % GPU, 47.9 tok/s; полный агентный цикл
  через pi на нём не измерялся — системный промпт занимает ~40 % окна.
- Причина `stopReason: length` при неполном `maxTokens` — гипотеза о недооценке кириллицы
  счётчиком pi не проверена прямым замером токенов Ollama.
- Сравнение `qwen3:8b` и `qwen3.5:9b` невозможно: второго тега нет.
- Эндпоинт `/v1` на bastion `11434` по-прежнему непригоден — перепроверять не требуется,
  вывод сделан на живом запросе.
