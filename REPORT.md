## 3. Модели

Фактические метаданные `qwen3.5:9b` (`/api/show`): архитектура `qwen35`, 9.0B параметров,
Q4_K_M (file_type 15), нативный контекст 262144, `embedding_length` 4096, 32 блока,
`head_count_kv` 4, `key_length` 256, `value_length` 256, полное внимание только в каждом
4-м слое (гибрид с SSM). Capabilities: `completion`, `tools`, `thinking` (по умолчанию включён), `vision`.

| Тег | Квант / размер | KV-кэш | VRAM (веса + KV + буферы) | GPU/CPU | decode | tool-calling | Вывод |
|---|---|---|---|---|---|---|---|
| `qwen3.5:9b`, 8192 | Q4_K_M, файл 6.6 GB | ≈17.4 KB/токен (расчёт по архитектуре, 8 full-attention слоёв, q8_0) | **5.62 GB, 100 % GPU** (измерено) | 0 / 100 % | **45.4–46.3 tok/s** | да, оба API | основной выбор |
| `qwen3.5:9b`, 16384 | то же | ≈0.29 GB | 6.49 GB всего, 5.69 GB в VRAM | 12.3 % / 87.7 % | 32.3 tok/s (короткий), 27.0 (промпт 7k) | да | компромисс |
| `qwen3.5:9b`, 24576 | то же | ≈0.43 GB | 6.68 GB всего, 5.58 GB в VRAM | 16.5 % / 83.5 % | 18.4–22.3 tok/s | да | только для разбора больших файлов |
| `qwen3:8b` | — | — | — | — | — | — | **не установлена** |
| `gpt-oss:20b` | оценка: Q4_K_M ≈ 11–12 GB | — | не влезает в 7.4 GB свободной VRAM → ≥40 % CPU | 40 %+ / <60 % | **оценка 5–10 tok/s**, не измерено | не проверено | нет: требует загрузки и, вероятно, непригодна по задержке |
| `crewai-qwen3-8b` | — | — | — | — | — | — | **не установлена** |

Пояснения к оценкам:

- KV-кэш посчитан по фактической архитектуре: 8 слоёв полного внимания × 2 (K+V) × 4 головы × 256
  → 16 384 элемента на токен; q8_0 ≈ 1.06 байт/элемент → **≈17.4 KB/токен**. Для 24576 это ≈0.43 GB.
- Наблюдаемые размеры растут нелинейно (8192 → 5.62 GB, 10240 → 6.31 GB): разницу дают
  вычислительные буферы, которые Ollama добавляет ступенями, а не сам KV-кэш.
- Строка `gpt-oss:20b` — **оценка по спецификации**, не измерение: модели на диске нет.
  Вывод «непригодна по задержке» основан на 8 GiB VRAM и не проверялся запуском.
- «Проверка tool-calling» — фактический вызов с JSON-схемой инструмента, см. §7.

**Резервная модель отсутствует.** Задание требует выбрать резервную «только из реально установленных
кандидатов» — таких нет. Вариантов два, оба требуют согласия: (а) работать без резерва,
(б) загрузить `crewai-qwen3-8b` (≈5.03 GB) и держать вторым тегом. Второй вариант упирается
в `OLLAMA_MAX_LOADED_MODELS=1` и в то, что две модели в 8 GiB не помещаются одновременно.

## 4. Предлагаемая конфигурация

Настройки Ollama в §4.1 — **предложение, не применено**. Конфигурация pi.dev в §4.2 применена

### 4.1 Ollama

| Параметр | Сейчас | Предлагается | Ожидаемый эффект | Проверка |
|---|---|---|---|---|
| `OLLAMA_CONTEXT_LENGTH` | 24576 | 8192 для агентной работы, 24576 оставить для разбора файлов | 45 vs 20 tok/s — разница в 2.2 раза на каждом шаге агента | `/api/ps` → `context_length` |
| `OLLAMA_NUM_PARALLEL` | 1 | 1 (оставить) | второй параллельный слот отнял бы VRAM у KV | `systemctl show ollama -p Environment` |
| `OLLAMA_MAX_LOADED_MODELS` | 1 | 1 (оставить) | вторая модель не влезает | `ollama ps` |
| `OLLAMA_KEEP_ALIVE` | 30m | 30m (оставить) | холодный старт 4.3–5.8 s на каждом шаге — недопустимо | `ollama ps` → `UNTIL` |
| `num_gpu`, `mlock`, `OLLAMA_NUM_THREADS` | не заданы | **не трогать** | mlock без запаса памяти вытеснит систему; потоки конкурируют со сборкой и тестами | — |

Ключевой факт для выбора контекста: `/v1` **игнорирует** `num_ctx` — проверено, `{"num_ctx": 8192}`
и `{"options":{"num_ctx":4096}}` в теле запроса дают `context_length: 24576` в `/api/ps`, то есть
серверный дефолт. Значит, pi.dev на `/v1` всегда получает 24576 и 20 tok/s, пока не изменён
серверный дефолт или тег модели.

Два способа получить 8192 для pi.dev. Первый применён 30.10.2026 по отдельной просьбе,
второй не применялся:

1. **Отдельный тег с параметром контекста** (blobs общие, веса не дублируются) — **выполнено
   30.10.2026**:
   ```bash
   printf 'FROM qwen3.5:9b\nPARAMETER num_ctx 8192\n' > /tmp/Modelfile-8k
   ollama create qwen3.5:9b-8k -f /tmp/Modelfile-8k
   # проверка: запрос через /v1 → /api/ps должен показать context_length 8192
   ollama rm qwen3.5:9b-8k   # откат
   ```
   Проверено: `ollama create` переиспользовал все слои весов (новый только манифест-слой);
   `/api/ps` после запроса через `/v1` показывает `model=qwen3.5:9b-8k`, `context_length=8192`,
   `size_vram=size=5.62 GB` (100 % GPU); decode 47.9 tok/s при `num_predict=300`, `think=false`.
   **Приоритет `PARAMETER num_ctx` над `OLLAMA_CONTEXT_LENGTH=24576` подтверждён.** Тег пока
   не подключён к pi.dev: системный промпт занимает ~3.3k токенов, то есть ~40 % окна 8192.
2. **Понизить `OLLAMA_CONTEXT_LENGTH` до 8192** — проще, но меняет поведение WebUI и агента
   `linuxmintai`, которым 24576 нужно для файлов на ~24k токенов; по README такой файл при
   16384 режется вдвое. Откат: вернуть значение из `override.conf.bak-20261030` и `systemctl daemon-reload`.

### 4.2 pi.dev

Установлен 2026-10-30: `pi 1.4.0`, `npm install -g --ignore-scripts @earendil-works/pi-coding-agent`.
Node.js 22.23.4 в PATH (требование pi — ≥22.19). npm кладёт бинарь в
`~/.local/node-v22.23.4-linux-x64/bin`, которого нет в `PATH`, поэтому сделан симлинк
`~/.local/bin/pi`.

Применённый `~/.pi/agent/models.json` (файл перечитывается при открытии `/model`):

```json
{
  "$schema": "https://pi.dev/schemas/models.schema.json",
  "providers": {
    "ollama": {
      "baseUrl": "http://127.0.0.1:11435/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        {
          "id": "qwen3.5:9b",
          "name": "qwen3.5 9B (local)",
          "contextWindow": 24576,
          "maxTokens": 2048,
          "samplingParams": { "temperature": 0.1, "top_p": 0.9 },
          "reasoning": true,
          "thinkingLevelMap": { "off": "none" },
          "compat": {
            "maxTokensField": "max_tokens",
            "supportsReasoningEffort": true,
            "thinkingFormat": "openai"
          }
        }
      ]
    }
  }
}
```

`pi --list-models` подтверждает разбор: `ollama  qwen3.5:9b  24.6K  2.0K  thinking:yes`.

`thinkingLevelMap.off` добавлен 2026-10-30 после A/B (§7.8): без него pi при `--thinking off`
не отправляет `reasoning_effort` вовсе (в коде бандла параметр ставится только если
`thinkingLevelMap.off` — строка), и Ollama думает по серверному умолчанию. Проверено зондом:
без маппинга прогон `off` дал 2 813 `thinking_delta`, с `"off": "none"` — 0.
`maxTokens` на время A/B поднимался до 8192 и возвращён к 2048; это лимит, а не резерв памяти.

Почему именно так:

- `baseUrl` — **напрямую на 11435**, не на bastion `11434`: bastion 0.6.0 на `/v1` возвращает
  один JSON `{"raw":"data: …[DONE]"}` вместо SSE (измерено), и агент, ждущий поток событий,
  получит один нераспознанный блок.
- `api: openai-completions` — единственный задокументированный тип API для локальных endpoint'ов.
- `apiKey` — фиктивная строка: Ollama её игнорирует, но pi требует поле для выбора модели.
- `samplingParams` поддерживается только для `openai-completions`/`openai-responses`;
  ключи `temperature`, `top_p`, `top_k` подтверждены документацией.
- **`contextWindow` и `maxTokens` обязательны.** На сайте pi.dev эти поля не показаны, но в
  установленном пакете они описаны в `docs/models-configuration.md` и
  `schemas/models.schema.json`. Дефолты — 128000 и 16384; с такими значениями pi считал бы,
  что модель держит 128k (Ollama реально даёт 24576) и мог бы обрезать ответ по 16k.
- `compat.maxTokensField: max_tokens` — Ollama ждёт `max_tokens`, а не `max_completion_tokens`
  (последний pi выбирает для OpenAI-хостов автоматически; для localhost лучше зафиксировать).
- `contextWindow` должен совпадать с фактическим `num_ctx` сервера: `/v1` не принимает `num_ctx`,
  поэтому при смене серверного дефолта это же число надо править здесь.


Управление инструментами — важная поправка к заданию. Задание предполагает, что в pi.dev
можно «не отключать подтверждения». Документация pi.dev говорит обратное: *«Pi does not ask for
approval before every tool call»*, инструменты работают с правами ОС-пользователя, встроенной
песочницы и режимов разрешений нет, `--approve`/`--no-approve` управляют только доверием
к проектным ресурсам. Поэтому меры переносятся на обвязку:

- запуск в одноразовом клоне (`git clone` в `~/tmp/…`, не в рабочем дереве);
- `-t read,write,edit` для первых прогонов, `bash` — только когда нужен запуск тестов;
- `--no-approve` для чужих каталогов, `--offline` где не нужен сеть;
- обязательный просмотр `git diff` перед переносом правок в рабочий репозиторий.

`.pidevignore` в документации pi.dev **не упоминается** — создавать не буду. Изоляция чтения
делается рабочей папкой, `-t`/`-xt` и `AGENTS.md`, а не выдуманным ignore-файлом.

## 5. Приватность и безопасность

- **Облачного маршрута нет и не предлагается.** `PROMPT.md:40` исключает OpenRouter и
  `free-model-proxy`; в системе их нет. Всё, что описано здесь, считается локально.
- **Единственный канал наружу** в текущем стеке — поиск через локальный SearXNG, и только
  по явному запросу. К агентной разработке он отношения не имеет.
- **pi.dev = права пользователя.** Ни подтверждений, ни песочницы. Опасные операции
  (рекурсивное удаление, `git reset --hard`, `git clean`, `dd`, установка пакетов, правка
  служб, драйверов, ядра, firewall, module/kernel-модули) в этом стеке не должны выполняться
  агентом вообще; при необходимости — вручную, после просмотра команды.
- **GPU-разлочка (`turing-unlock`) и смена драйвера/ядра** — вне области этой задачи:
  никаких автоматических применений, только отдельный обратимый эксперимент с согласием.
- **Секреты:** ключей нет по построению; в отчёт и скрипты ничего не попадает. Конфиг
  bastion (`~/.config/bastion/broker.yaml`) не содержит секретов.

### 7.1 Старт и скорость

|---|---|---|---|---|---|---|
| 4096 | 0 % | 5.54 / 5.54 GB | 45.1 tok/s | — | — | — |
| **8192** | **0 %** | **5.62 / 5.62 GB** | **45.4–46.3 tok/s** | 34.4 (7 150 tok) | 1 365 tok/s | 0.14–0.22 s |
| 10240 | 12.5 % | 6.31 / 5.52 GB | 34.5 tok/s | — | — | — |
| 12288 | 12.5 % | 6.35 / 5.56 GB | 34.7 tok/s | — | — | — |
| 14336 | 12.4 % | 6.40 / 5.60 GB | 35.4 tok/s | — | — | — |
| 16384 | 12.3 % | 6.49 / 5.69 GB | 32.3 tok/s | 27.0 (7 150 tok) | 1 284 tok/s | — |
| 24576 (текущий) | 16.5 % | 6.68 / 5.58 GB | 18.4–22.3 tok/s | 23.8 (14 279 tok) | 1 185 tok/s | 0.18–0.22 s |

- Холодный старт: **4.3–5.8 s** только загрузка весов; первый токен приходит через 4.8–5.8 s.
- Длинная генерация (900 токенов) при 24576: 22.3 tok/s, SM 1908 МГц в среднем, 146 W из 215 W,
  63 °C, GPU-util 45 % — упор не в мощность и не в температуру, а в CPU-offload.
- Снижение decode при длинном промпте — это цена внимания по 7–14k токенов, а не ошибка замера.
- Разброс между повторами на одной конфигурации: ±3 %, кроме перехода через границу offload.

**Расхождение с README `linuxmintai`** (там 47 tok/s при 16384 и 35 при 24576) объясняется
не ошибкой, а тем, что скорость определяет не `num_ctx` сам по себе, а доля слоёв, выбранная
планировщиком по свободной VRAM в момент загрузки. Сегодня рабочий стол занимает 615 MiB VRAM,
и 24576 грузится с 16.5 % CPU → 20 tok/s. Цифры из README воспроизводятся при 12.4 % offload
(сегодня это соответствует 16384 → 32–35 tok/s). Для агентной работы важна именно эта граница.

Журнал Ollama за три прогона §7.5: 17 запросов, 5 384 новых prompt-токена (остальное прочитано

причина расхождения не установлена (вероятно, другой остаток VRAM под буферы в момент прогона).

**Есть ли выигрыш.**

- *По токенам — нет.* Запросы те же, а через pi.dev даже длиннее: системный промпт с описанием
  инструментов занимает ~3.3k токенов, то есть около 40 % восьмитысячного окна.
- *По деньгам и квоте — да, но небольшой.* Одна задача ≈800–900 выходных токенов; в облаке это

  лимит подписки, работает без сети и не отправляет код наружу (§5).
- *По времени — проигрыш.* 6–15 s «голым» циклом и 57–91 s через pi.dev на задачу; облачный
  агент на том же объёме будет в разы быстрее. Если время дороже центов, локальная модель
  проигрывает.

**Практический резерв скорости.** Тег с `num_ctx 8192` даёт 45 tok/s вместо 10–20 (§6, шаг 4),
но системный промпт pi.dev съедает 40 % такого окна. Компромисс — 16384 (27–32 tok/s, §7.1).
Оба варианта не применялись.

обвязки. Прогоны на реальном репозитории (§7.7) эту картину не подтвердили.

### 7.7 Реальный репозиторий HeadPhones: прогоны 1–4

Одноразовый клон `~/tmp/pi-real-hp` из `~/Документы/HeadPhones` (коммит `af6547f`).
В клон добавлен `AGENTS.md` с ограничениями (менять только `tools/btsnoop.py` и
`tests/test_btsnoop.py`, не коммитить, не трогать `app-probe/`), он закоммичен отдельно как
часть обвязки. Базовая линия до прогонов: `bash test.sh` зелёный — 8 Python-тестов и 11 Kotlin,
5.8 s.

Задача взята из бэклога самого репозитория (`docs/task-brief.md` §A.6.2 и
`docs/hq36-protocol.md`): реализовать разбор ответа `0x54` — функцию `eq_bands_of(frame)`,
строку в `decode_value()`, тесты и прогон `python3 tests/test_btsnoop.py`.

| Прогон | Задача | Ходов / инструментов | Время | Итог |
|---|---|---|---|---|
| 1 | реализовать разбор `0x54` | 6 / 9 (`read`×6, `edit`×2, `bash`×1) | 5 мин 24 с | код верный, тесты неверные → **FAILED (failures=1, errors=1)** |
| 2 | починить падающие тесты | 3 / 3 (`bash`, `read`×2) | 3 мин 14 с | правок нет, оборвался на `maxTokens: 2048` |
| 3 | починить падающие тесты, `maxTokens: 4096` | 6 / 6 (`bash`×3, `read`×2, `edit`×1) | 8 мин 27 с | добавил отладочные `print`, причину увидел, но не исправил; **FAILED**, финальный ответ оборван |
| 4 | та же починка, но с подсказкой «fixture = 70 байт, 10×7»; три попытки: `maxTokens` 2048 / 4096 / 8192 | 2–4 / 3 (`read`×3) | 3 мин 41 с / 4 мин 17 с / 7 мин 44 с | правок нет ни в одной попытке; **FAILED** во всех трёх |

**Прогон 1.** Модель прочитала протокол и оба файла, затем добавила в `tools/btsnoop.py`
24 строки: `eq_bands_of` с корректной раскладкой (10 записей по 7 байт, u16 BE для gain/freq/Q)
и строку в `decode_value`. Реализация соответствует `docs/hq36-protocol.md`.

Тесты она сочинила неверно: payload собран по **6 байт на полосу** (60 байт при заголовке
`len=0x46` = 70), gain записан как `0x9632` вместо `0x079E` (1950). В результате
`eq_bands_of` возвращает `None`, падают `test_eq_bands_parse` (TypeError) и
`test_eq_bands_in_report` (в отчёте нет строки про полосы). То есть модель написала рабочий
код и тут же — фикстуру, противоречащую собственному чтению спецификации.

**Прогон 2** (свежая сессия, в том же клоне): запустила тесты, перечитала `tools/btsnoop.py`
и `tests/test_btsnoop.py`, правок не внесла. Последний ответ оборван на лимите
`maxTokens: 2048` (`stopReason: length`, `output: 2048`); в прогоне 1 финальный
диагностический ответ тоже оборван (`output: 1`).

**Прогон 3** — проверка гипотезы «виноват лимит»: `maxTokens` временно поднят до 4096
(резервная копия `~/.pi/agent/models.json.bak-2048`, после прогона конфиг восстановлен).
Модель запустила тесты, добавила в `eq_bands_of` отладочные `print` и прогнала тесты снова.
Отладочный вывод показал корень проблемы: `len(p)=60, expected=70` — те же 6 байт на полосу.
То есть модель **увидела** причину, но вместо правки фикстуры запустила тесты ещё раз и
снова оборвалась (`stopReason: length`, `output: 2944` при лимите 4096; почему остановка
раньше лимита — не установлено). Итог тот же:
**FAILED (failures=1, errors=1)**, плюс в продакшн-коде остались отладочные `print`.

**Прогон 4** — с подсказкой: «payload кадра `0x54` должен быть ровно 70 байт, 10 записей
по 7 байт». Три попытки подряд на одном и том же состоянии клона:

- `maxTokens: 2048` — модель **правильно** диагностировала обе ошибки фикстуры (6 байт вместо 7;
  gain `0x9632` вместо `0x079E`), объявила «Исправлю тесты» и оборвалась на 2048 токенах,
  не дойдя до правки;
- `maxTokens: 4096` — на этот раз ошибочно решила, что виновата контрольная сумма,
  снова объявила о правке и оборвалась на 2605 токенах. Контекст при этом не был исчерпан
  (21 261 из 24 576, `truncated = 0`), то есть сработал не `n_ctx`;
- `maxTokens: 8192` — ушла в повторяющееся рассуждение: один и тот же абзац про «пример
  `01 060E 004A 0050` — это 4 байта, а должно быть 7» повторялся в thinking, 6 122 токена
  вывода, затем контекст исчерпан (24 575 из 24 576, `truncated = 1`). Правок нет.

Итог прогона 4: **0/3 попыток**, набор тестов остался красным, отладочные `print` в
`tools/btsnoop.py` не убраны. Подсказка иногда исправляет диагностику, но не превращается
в действие: модель тратит весь бюджет вывода на рассуждение и зацикливается на подсчёте
байтов. После эксперимента `maxTokens` возвращён к 2048 (резервная копия
`~/.pi/agent/models.json.bak-2048`).

**Вывод.** На синтетических песочницах (§7.5) результат был 3/3; в прогонах 1–4 на реальном
репозитории — **0/4** (с A/B §7.8 — 0/6). Разница не в tool-calling: инструменты работали,
ошибки чтения исправлялись.
Разница в верификации: модель не удержала соответствие между спецификацией, реализацией и
собственным тестом; увидев расхождение в отладочном выводе, не перешла к исправлению.
Повышение лимита вывода до 4096 и 8192 проблему не решило: на 8192 модель зациклилась
и исчерпала контекст. Это подтверждает главный риск из §1 и показывает, что успех §7.5
частично объясняется простотой фикстур.

## 8. Не делать

1. **Не поднимать `num_ctx` выше 16384 «на всякий случай».** При 24576 в CPU уходит 16.5 % слоёв,
   decode падает с 45 до 18–22 tok/s, и каждый шаг агента становится в 2–2.5 раза дольше.
2. **Не направлять pi.dev на bastion `11434`.** Он буферизует `/v1` в один JSON; агент,
   ожидающий SSE, получит нераспознанный ответ. Только напрямую `127.0.0.1:11435`.
3. **Не рассчитывать на `gpt-oss:20b` как на резерв.** Модели нет на диске, а 20B в Q4 не влезает
   в 7.4 GB свободной VRAM: ≥40 % слоёв уйдёт в CPU с оценкой 5–10 tok/s — это не резерв,
   а другой режим работы, и он не проверен.
4. **Не давать pi.dev `bash` без внешней изоляции.** У него нет ни подтверждений команд,
   ни песочницы — только права вашего пользователя; первый прогон должен быть в одноразовом клоне
   с последующим `git diff`. В трёх прогонах §7.5 агент границы каталога не нарушал, но это
   свойство промпта и песочницы, а не гарантия pi.dev.
5. **Не включать облачный маршрут как «фолбэк при ошибке».** Ни в pi.dev, ни в скриптах:
   автоматический переход на OpenRouter отправит код наружу без отдельного разрешения.
6. **Не считать `--thinking off` выключенным без `thinkingLevelMap.off`.** Без маппинга pi не
   отправляет `reasoning_effort`, и модель думает по умолчанию. Проверка: в логе прогона должно
   быть 0 `thinking_delta`, а `thinkingLevel` — `off` (§7.8).
7. **Не доверять `PLANPR.md`/`LOGPR.md` без внешней сверки.** Модель ставит выдуманную дату,
   а «OK» может быть получен правкой теста вопреки `AGENTS.md`. Проверять `git diff`, повторно
   запускать тесты и сверять дату с системной (§7.9).
